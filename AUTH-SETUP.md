_Everything here is Supabase dashboard configuration. It cannot be done from the repo,
so it is the checklist for whoever owns the Supabase project._

Supabase project: `zafozgadkffumhvxtzmq`
Production site: `https://lyamfi.com`

## 0. Run the schema first

Paste `supabase/setup.sql` into **SQL Editor → Run**. It is generated by
`scripts/build-setup-sql.py` from `supabase/migrations/*.sql` and is safe to re-run:
every statement is guarded (`IF NOT EXISTS`, `DROP ... IF EXISTS` before policies and
triggers, `CREATE OR REPLACE` for functions, `ON CONFLICT` on every seed insert).

"Success. No rows returned" is the expected output: the script is all DDL.

### Verify it landed

```sql
select level, count(*) as lessons
from public.lessons group by level order by level;
```

Expect **Avancé 6, Débutant 4, Intermédiaire 4**: the 14 modules from the course PDF.

```sql
select u.email,
       coalesce(r.role, 'aucun') as role,
       (u.email_confirmed_at is not null) as confirmed,
       r.granted_at
from auth.users u
left join public.user_roles r on r.user_id = u.id
order by u.created_at;
```

Shows every account and its role.

## 1. Create the admin account

**No password is stored in this repository, deliberately.** The repo is public: a
committed credential would be readable by anyone. Instead the migration
`20260819090000_admin_roles.sql` grants the admin role **by e-mail address**:

```sql
CASE WHEN lower(NEW.email) = 'lyamcorpo@gmail.com' THEN 'admin' ELSE 'user' END
```

So the account becomes an admin automatically, whenever it is created:

1. Go to the live site → **Créer un compte gratuit**
2. Sign up as `lyamcorpo@gmail.com` with the password you chose
3. Confirm the e-mail
4. Sign in: an **Admin** link appears in the navbar, and `/admin` opens

If the account already existed before the migration ran, the migration's backfill
(same file, `UPDATE public.user_roles SET role = 'admin' ... WHERE lower(u.email) = ...`)
promotes it on the spot. Nothing else to do.

> ⚠️ The password for this account was shared in a chat transcript during setup.
> Change it once you're in, via **Mon compte → Changer le mot de passe**.

### Adding more admins later

The principal admin promotes anyone from `/admin`, using the "Rendre admin" button.
That's meant for handing customer support to someone else.

**Two tiers, enforced in the database:**

| | Principal (`lyamcorpo@gmail.com`) | Secondary admin |
|---|---|---|
| See accounts and their activity | ✅ | ✅ |
| Grant or revoke admin | ✅ | ❌ |
| Rename an account | ✅ | ❌ |
| Reset a password | ✅ | ❌ |
| Delete an account | ✅ | ❌ |

Every sensitive RPC starts with `is_principal_admin()`, which resolves the caller's
address from `auth.users`. Hiding the buttons is cosmetic; the database is the
barrier. The principal account cannot be deleted or demoted by anyone, including
itself, so the console can never become permanently unreachable.

### Reading a password is not possible, for anyone

`auth.users.encrypted_password` holds a **bcrypt digest**, a one-way function. The
password a user typed is stored nowhere, so no query and no privilege level can
return it. That is exactly what protects every account if the database leaks.

What the principal admin can do instead, from a account's profile page: set a **new**
password. The panel generates one, shows it once, copies it, and deletes that
account's open sessions so a device already signed in loses access. Pass it on
through a safe channel and ask the holder to change it from **Mon compte**.

### Names

Signup now asks for a first and last name. The dashboard greets **Bonjour
{prénom}** instead of the e-mail. The last name is uppercased and the first name
capitalised automatically by a database trigger, so `el fassi` is stored as
`EL FASSI` whichever screen wrote it.

Accounts created before this ran are named by the migration's backfill:
`lyamcorpo@gmail.com` becomes **Lyamfi**, an address containing `rayane` becomes
**Rayane LYAMOURI**, one containing `hassan` becomes **Hassan LYAMOURI**. Anything
the heuristic missed can be set by hand, either by the account holder under
**Mon compte** or by the principal admin from the account's profile page.

## 2. Redirect URLs: do this before testing password reset

Supabase refuses to redirect to a URL that isn't allow-listed, and the failure looks
like a broken reset link rather than a config error. This bites everyone once.

**Dashboard → Authentication → URL Configuration:**

| Field | Value |
|---|---|
| Site URL | `https://lyamfi.com` |
| Redirect URLs | `https://lyamfi.com/**` |

Add `http://localhost:5173/**` too if you want password reset to work against the dev
server. If you test on the Cloudflare preview URL (`*.workers.dev` / `*.pages.dev`),
add that pattern as well. It is a different origin, so it needs its own entry.

The app requests these two redirect targets, both built from `window.location.origin`
(`src/routes/auth.tsx`):

- `${origin}/reset-password`: password recovery
- `${origin}/dashboard`: e-mail confirmation after signup

The `/**` wildcard covers both, which is why one line is enough.

## 3. Use your own e-mail sender

Confirmation and reset e-mails currently go out through Supabase's **built-in**
sender. That is fine for testing but not for launch: it is rate-limited to a handful
of messages per hour, and it sends from a Supabase-owned domain, so real signups tend
to land in spam.

Fix: point Supabase at your own SMTP provider.

### Pick a provider

| Provider | Free tier | Notes |
|---|---|---|
| **Resend** | 3 000/month | Simplest setup, good deliverability. Recommended. |
| Brevo | 300/day | Generous, EU-based |
| Mailgun / SendGrid | limited trials | Fine if you already use them |

### Wire it up

1. Create the account, **verify `lyamfi.com` as a sending domain** (add the DKIM/SPF
   DNS records they give you: in Cloudflare DNS, since the domain is there. Without
   this, mail lands in spam.)
2. Generate an SMTP username + password
3. **Supabase → Project Settings → Authentication → SMTP Settings** → *Enable Custom SMTP*:

   | Field | Value |
   |---|---|
   | Sender email | `no-reply@lyamfi.com` |
   | Sender name | `Lyamfi` |
   | Host | e.g. `smtp.resend.com` |
   | Port | `465` |
   | Username / Password | from the provider |

4. **Save**, then send yourself a test signup.

### Translate the e-mails

The app is in French but Supabase's default templates are English.
**Authentication → Email Templates**: edit *Confirm signup* and *Reset password*.
Keep the `{{ .ConfirmationURL }}` variable exactly as-is; everything around it is yours.

## 5. Password rules

Enforced client-side in `src/lib/password.ts` and shown live as a checklist during
signup and reset: the user sees exactly which condition is missing rather than a
bare "password not secure":

- at least 8 characters
- one lowercase letter
- one uppercase letter
- one digit
- one special character

Supabase has its own minimum (6 by default). Raise it to match under
**Authentication → Providers → Email → Minimum password length**, so the rule holds
even if someone calls the API directly.

## 6. What protects the admin page

Worth understanding, because the visible part is the least important part.

| Layer | What it does | Load-bearing? |
|---|---|---|
| Navbar link hidden for non-admins | cosmetic | no |
| `/admin` route shows "Accès réservé" | cosmetic | no |
| **`is_admin()` re-checked inside every RPC** | rejects the call | **yes** |
| **No INSERT/UPDATE/DELETE granted on `user_roles`** | role can't be self-assigned | **yes** |

The anon key ships in the client bundle, so any logged-in user can call the API
directly with their own token. That's expected and fine: the database refuses them.
The two bold rows are the actual security boundary; if you change them, re-check this.

Specifically: `user_roles` grants `authenticated` **SELECT only**. Every write goes
through `admin_set_role()`, which is `SECURITY DEFINER` and re-checks `is_admin()`
before touching anything. Without that split, a user could simply `UPDATE` their own
row to `admin`.
